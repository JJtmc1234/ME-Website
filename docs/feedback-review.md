# Community feedback review

Use the existing shared feedback document for intake. The website explains the process at
`/feedback`. No new ticketing service is required.

For each entry, record:

| Field | What to write |
| --- | --- |
| Category | Idea, Concern, Correction, Question, or Action item |
| ME area | The product, research direction, or company plan affected |
| Summary | Preserve the substance of the original entry |
| Current plan changes | Yes or no, with a reason |
| Outcome | Act now, answer, keep for later, or needs clarification |
| Next step | A concrete action, an answer, or a condition for revisiting the idea |
| Review date | The date somebody actually reviewed the entry |

Corrections to public facts come first. Concerns require an explicit response about the risk.
Questions receive an answer or identify missing documentation. Action items need an owner
and a checkable result before being treated as assigned work.

Ideas that do not fit current work stay in a keep for later section. Record why the idea
is deferred and what would make it worth revisiting. Do not silently delete or relabel it
as rejected because it cannot be implemented today. JJ makes final decisions on ME plans.

Only publish sanitized summaries in `data/feedback.ts`. Never include private contact details,
internal discussion, account identifiers, or private document links. Do not invent review
outcomes to populate the page. Existing public entries remain attributed only as authorized
by their author.
